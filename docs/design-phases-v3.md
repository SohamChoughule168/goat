# Imaginars v3 — phased prompts for OpenCode

Five prompts. **Paste one at a time.** Do not paste Phase N+1 until Phase N's gate output is in front of you and passing. That sequencing is the point: build 2 and build 3 both built chrome first and evidence last, and both came out thin.

**Before Phase 0:** copy `design-spec-v3.md`, `tokens.css`, and `palette.py` into the repo root (Phase 0 will move them into place). Answer the five positioning questions in §12 of the spec if you can — Phase 2 will otherwise leave visible `TODO(positioning)` markers rather than invent copy.

**Time expectation:** Phase 0 ~10 min, Phase 1 ~45 min, Phase 2 is the long one (content, 2–3 h), Phase 3 ~1 h, Phase 4 ~1.5 h, Phase 5 ~45 min.

---

## PHASE 0 — setup, audit, no design

```
Read design-spec-v3.md fully before doing anything. It is authoritative and supersedes design-brief.md and design-brief-v2.md.

Do this phase and then STOP for review. Write no design code in this phase.

1. Create branch v3-professional off main. Confirm: production imaginarsclubservices.com and the staging goat-wheat.vercel.app deployment must remain untouched by every phase in this project. Never push to main. Never run a production deploy. If a step would touch production, stop and ask.

2. Move design-spec-v3.md to docs/design-spec-v3.md, tokens.css to src/styles/tokens.css, palette.py to scripts/palette.py. Commit as "docs: adopt v3 professional spec".

3. Verify the toolchain actually works before relying on it later:
   - Playwright installed with browsers downloaded; take one screenshot of the current homepage to prove it
   - Lighthouse runnable from CLI
   - axe-core runnable against a served build
   - Print the version of each
   If any of these is missing, install it now. Do not proceed on the assumption that a tool exists.

4. Inventory the repo and write docs/v3-inventory.md answering, with file paths as evidence:
   - What content exists in the content layer right now: how many services have real copy, how many case studies, how many articles, how many client logos, how many testimonials
   - For each of the 18 services, which of these fields are populated and which are empty: description, deliverables, timeline, exclusions, price band, FAQs, related services
   - Which components hardcode colour values (list them; grep for hex, rgb(, oklch( in component files)
   - What fonts are currently loaded and how
   - Current route count vs the 40+ target in spec §8
   - What real image assets exist, their dimensions, and whether any have dark-mode variants

5. Write docs/v3-content-gaps.md: a precise list of what content is missing to satisfy the content floor C1–C8 in spec §5, as a checklist Soham can fill in. Be specific — "service 'Brand Systems' needs deliverables list and price band", not "some services need copy".

Then STOP. Report: the inventory summary, the content gap count, and any tool that was missing.
```

**Gate 0 — do not continue until:** branch exists, all four tools print a version, one real screenshot exists, and both docs are written. If the content gap list is large, fill what you can before Phase 2 — that phase is where thinness gets locked in.

## PHASE 1 — tokens, dual mode, primitives

```
Read docs/design-spec-v3.md sections 3, 4, 7, 8b, 9, 10 before starting.

Build the token layer and the theme system. No page layout in this phase.

1. Wire src/styles/tokens.css as the single source of colour, space, radius, type, and motion values. It is generated by scripts/palette.py — never hand-edit it. If a value needs to change, change the ramp in palette.py and re-run it.

2. Port palette.py's verification into scripts/contrast-ci.mjs: same OKLCH→sRGB conversion, same WCAG contrast maths, same 26 semantic pairings, both modes. It must exit non-zero on any pairing below target. Wire it into the test script so it runs in CI. Confirm it reproduces these numbers: light text-on-bg 19.07:1, light accent-on-bg 4.89:1, dark accent-on-bg 7.65:1, dark text-subtle-on-surface 4.69:1, light accent-on-accent-subtle 4.63:1. If your port disagrees with palette.py, your port is wrong — fix it until they match.

3. Implement the three-state theme system exactly per spec §7:
   - System / Light / Dark, as a segmented control with role="radiogroup", visible current state, real labels
   - The inline blocking head script from the spec, before any paint
   - Persist to localStorage key 'imaginars-theme'
   - Two <meta name="theme-color"> tags with media attributes
   - color-scheme set in both modes
   - Instant swap. Optional View Transitions circular reveal, 350ms, ease-emphasis, skipped when unsupported and disabled under prefers-reduced-motion
   - Do NOT transition background-color or any colour property globally on swap

4. Add scripts/token-lint.mjs: fail the build if any file under src/components or src/app contains a raw hex, rgb(), hsl(), or oklch() literal, or a spacing value not on the scale in tokens.css. Add an allowlist file for genuine exceptions and keep it near-empty. Fix every violation the Phase 0 inventory found.

5. Add scripts/theme-audit.mjs using Playwright:
   - Load every route with a cold cache, with OS preference set to dark and again to light
   - Screenshot at first paint and assert no flash of the wrong theme (compare the first-paint pixel at the top-left against the expected bg token)
   - Assert every --color-* token in tokens.css resolves to a non-empty computed value in both modes
   - Run axe against every route in both modes; fail on any serious or critical violation

6. Build or restyle the primitive set, each with all states designed in both modes: default, hover, active, focus-visible, disabled, loading, error, selected. Button (variants: primary, secondary, ghost, danger; sizes sm/md/lg where each size sets height, padding, font size, icon size, and radius together), Input, Select, Textarea, Checkbox, Radio, Switch, Card, Badge, Table, Tabs, Dialog, Popover, Tooltip, Breadcrumb, Pagination, Skeleton, EmptyState, ErrorState.
   For anything with focus management, keyboard interaction, or portalling — dialog, popover, select, combobox, tabs, tooltip, menu — build on a tested headless primitive library rather than hand-rolling. Resolve the current package name, install command, and import paths from official docs or Context7 before writing code; do not rely on remembered APIs.
   Every component uses tier-2 tokens only. If a copied registry component is still recognisable as coming from that registry, restyle it further.

7. Set up fonts: Geist Sans variable and Geist Mono via next/font with display swap and preload, subset to latin. Newsreader loaded only on /insights routes. Remove Clash Display and its files entirely.

8. Build a /design-system route (noindex) rendering every primitive in every state, both modes, plus the full type scale, spacing scale, and both colour ramps with live computed contrast ratios printed next to each pairing.

9. Build the layout primitives from spec §8b, since every later phase depends on them: Container (max 1280px; gutters 24px below 768, 40px to 1280, 64px above), a 12-column Grid (24px gap desktop, 16px mobile), Section (padding ≥96px mobile, ≥128px desktop), Prose (680px measure), and FullBleed (1440px track, imagery only). Breakpoints 375 / 640 / 768 / 1024 / 1280 / 1440. Asymmetric splits are 7/5 or 8/4 only — do not add a 6/6 variant.

Then STOP and report the output of: contrast-ci, token-lint, theme-audit, lint, tsc, tests. Attach screenshots of /design-system in both modes at 1440 and 375.
```

**Gate 1 — all must pass:** `contrast-ci` 26/26 both modes · `token-lint` zero violations · `theme-audit` zero flashes and zero serious/critical axe issues on every route in both modes · lint clean · `tsc` clean · tests green · `/design-system` screenshots show every state in both modes.

## PHASE 2 — content depth (the phase that decides whether this reads as a real company)

```
Read docs/design-spec-v3.md sections 5, 8, 11, 12 before starting.

This phase is content architecture, not art direction. Use plain, token-styled layouts. Phase 3 does the art direction. Building visual polish before the content exists is the mistake that produced the last two rejected builds.

HARD RULE ON CONTENT: use only real content that exists in the repo or that Soham has supplied. Never invent a client name, a metric, a testimonial, a logo, or a date. If a required field has no real value, render a visible TODO(content: <what is needed>) marker in the build and list it in docs/v3-content-gaps.md. A visible gap is acceptable; fabricated proof is not.

Check content/positioning.md. If it does not exist or the five questions in spec §12 are unanswered, build every template but leave the hero, the value proposition, and all case study claims as visible TODO(positioning) markers. Do not write that copy yourself.

1. Extend the content layer schema so a service has: slug, name, practice area, summary, body (≥400 words), deliverables[], timeline, processStages[], exclusions[], priceBand, faqs[] (≥3), relatedServices[], caseStudyRef. Validate at build time with a schema — a service missing a required field fails the build rather than rendering empty.

2. Build the full route tree from spec §8. Every route real and reachable: /services, /services/[slug] × 18, /work, /work/[slug], /pricing, /estimate, /process, /about, /trust, /insights, /insights/[slug], /careers, /careers/[slug], /contact, /faq, /legal/privacy, /legal/terms, /legal/cookies, 404, 500.

3. Service detail template with every field from the schema surfaced, including "what this does not include". FAQPage JSON-LD from the faqs array.

4. Case study template: problem, constraints, approach, what was built, quantified outcomes (≥2), duration, services used, client quote where cleared, live link where public, and an honest confidentiality note where detail cannot be shown. Filterable index by practice area.

5. /pricing: ≥3 tiers, a real comparison table with tabular numerals, what each tier includes and excludes, and a clear entry point to /estimate. If the price bands are not yet decided, mark them TODO(positioning) — do not guess numbers.

6. /process: the four stages documented in real depth — what happens, what the client does, what they receive, how long it takes, what goes wrong and how it is handled.

7. /trust: confidentiality posture, data handling, where client material is stored, subcontractor policy, IP ownership on delivery, engagement terms. Written plainly. This page is what a larger buyer checks; treat it as a real deliverable.

8. /insights: article index plus MDX article route with reading time, publish date, author, tags, Article JSON-LD, and Newsreader body at 19px/1.7. If fewer than six real articles exist, list what is missing in the gaps doc rather than generating filler articles.

9. /careers, /faq, /about (story, team, operating principles, real numbers), /contact (form with server action, real validation states, honest response-time commitment).

10. SEO plumbing: per-route metadata, canonical URLs, Organization + Service + BreadcrumbList + FAQPage + Article JSON-LD, sitemap.xml generated from the route tree, robots.txt, rss.xml for insights, llms.txt.

11. Write scripts/depth-audit.mjs enforcing content floor C1–C8 from spec §5 as a build-failing check. It must count real published content, not templates: a service page with a TODO marker does not count toward C1.

Then STOP and report: depth-audit output with each of C1–C8 pass/fail and its actual count, total route count, and the full list of TODO markers by type.
```

**Gate 2 — the important one.** `depth-audit` must report actual counts for C1–C8. Items blocked purely on content Soham has not supplied may fail *provided* every one is listed as a TODO with a specific ask. Anything failing because the template does not surface the field is a build failure. Route count ≥ 40. No fabricated names, numbers, or quotes anywhere — spot-check three case study claims against source.

## PHASE 3 — art direction

```
Read docs/design-spec-v3.md sections 2, 4, 6, 8b, 9, 10 before starting.

Now art-direct what Phase 2 built. Content stays; presentation changes.

1. Build the header and footer exactly per spec §8b. The header's Services mega-menu is the highest-value item in this phase — four practice-area columns listing all 18 services with one-line descriptors, plus a fifth column with the featured case study. Built on a tested headless menu primitive (resolve its current API from official docs or Context7 first), 120ms hover intent delay, opens on focus for keyboard, closes on Escape, and degrades to a plain nested <ul> without JS. Mobile is a full-height drawer with practice-area accordions. The footer is five columns plus a base row carrying the registered entity name and registration number.

2. Home page. Sections, in order: hero (display type at clamp(2.75rem, 6.2vw, 7rem), 21-word lede at 45–60ch, two CTAs) · client logo wall, ≥6 real logos with per-mode variants · the Capability Graph · three quantified proof points in Geist Mono tabular figures, pulled from the content layer — if fewer than three real numbers exist, mark TODO(content) rather than inventing one · lead case study with real imagery at ≥60vw · practice areas as four indexed rows · the four-stage process · testimonial with name, role, company · pricing posture with link to estimator · closing CTA.
   Vary the section rhythm: alternate full-bleed, narrow measure (680px), and asymmetric 7/5 or 8/4 splits. Six identical centred sections is the templated tell. Section padding ≥128px desktop, ≥96px mobile.

3. Build the Capability Graph per spec §6, using the exact geometry given there — viewBox 960×720, hubs at 168px radius, service nodes at 300px radius clustered ±32° from their parent, 1px quadratic connectors with the control point pulled 40% toward centre, Geist Mono 11px labels. Do not invent the layout. Below 768px replace the radial form with four stacked indexed columns rather than shrinking it.
   - This is the ONE motion signature: strokes draw in via stroke-dashoffset, 900ms, ease-decel, 40ms stagger capped at 8 elements, triggered once on scroll into view. Nothing else on the site gets a signature animation.
   - Initial state visible in CSS; hide via JS only after confirming the animation code loaded, so a JS failure never leaves content at opacity 0.
   - Read the "honest risk" note in spec §6. If at Gate 3 this reads as a mind-mapping gimmick rather than a technical drawing, say so plainly in your report and propose the documented fallback instead of defending it.

4. Art-direct the four content templates. Do not improvise the structure — use these:
   - Service page: 8/4 split. Left column is the body at 680px measure with h2 section anchors; right column is a sticky card (top offset 96px) holding price band, timeline, deliverables count, and the CTA. Full-bleed related-case-study band above the footer. scroll-margin-top: 96px on every anchor target.
   - Case study: full-bleed hero image at 100vw × 62vh with the title overlaid on a bottom scrim; then a 3-column metadata strip (client, duration, services) in Geist Mono; then alternating 7/5 text-and-image blocks; then outcomes as large tabular figures at h2 size with mono labels beneath.
   - Pricing: three tier cards above the fold, then the full comparison table below at container width, sticky table header, tabular numerals, row hover highlight, and a mono footnote row.
   - Insights article: 680px Newsreader body at 19px/1.7, drop-capital-free, a right-hand table of contents that becomes a top progress bar below 1024px, pull quotes at h3 size in Geist Sans set outside the measure with a hanging left rule.

5. Image treatment system: one consistent grade across all client visuals, 1px inner border at --color-border-hairline, per-mode brightness handled on a wrapper via CSS filter and not baked into assets, considered focal points, next/image with correct sizes.

6. Functional motion only, everywhere else: hover 160ms, micro-feedback 100ms, popovers 200ms, panels 300ms, route transitions 420ms. Entrances decelerate, exits accelerate and are 0.6–0.8× the enter duration. Transform and opacity only — nothing that animates width, height, top, left, background-color, box-shadow, or filter. Reach for CSS before any library; if a library is needed, resolve its current API from official docs or Context7 first.

7. Update scripts/motion-audit.mjs to assert: exactly one signature animation exists, every reveal ends visible, prefers-reduced-motion removes all movement while keeping opacity fades, and no animation targets a layout or paint property.

8. Update scripts/presence-floor.mjs for P1–P6 and scripts/ratio-audit.mjs to measure the real computed display:body font-size ratio at 1440 in the browser. Assert ≥6:1. Add a check that no accent-filled element exceeds 480 × 320px (spec §10).

Then STOP and report: presence-floor P1–P6 with measured values, ratio-audit's actual measured ratio, motion-audit, and screenshots of every major route in both modes at 1440, 768, and 375.
```

**Gate 3 —** P1–P6 pass with measured numbers, not claims · type ratio ≥6:1 measured in-browser · exactly one signature animation · no accent-filled area over 480×320px · Capability Graph works with JS disabled and via keyboard only · screenshots at all three widths in both modes · axe still 0 serious/critical in both modes.

**Gate 3 also has a human step, and it is the one that actually matters.** Every other gate is a script; none of them can tell you whether the page looks expensive. Before pasting Phase 4, open the screenshots yourself and answer three questions in writing: does the header mega-menu make the company look bigger than it did? Does the Capability Graph read as a technical drawing or as a mind-mapping app? Is there any section you would describe as "basic"? If the answer to the third is yes, name the section and fix it in Phase 3 rather than carrying it into Phase 4 — the previous two builds were both signed off on gate output rather than on looking.

## PHASE 4 — features

```
Read docs/design-spec-v3.md sections 6, 9 before starting.

1. Scope Estimator at /estimate. Inputs: practice area, scope size, timeline, ongoing support level. Output: a real price band and indicative timeline, derived from a documented rules table in the content layer — not a random number. "Email me this estimate" captures the lead via a server action. Designed empty, loading, error, and success states in both modes. Must work as a plain multi-step form with JavaScript disabled. If the price rules are not yet decided, mark TODO(positioning) and ship the mechanism with placeholder rules clearly labelled as such in the UI.

2. Site search, Cmd/Ctrl-K. Indexes services, case studies, insights, and FAQ at build time. Keyboard-first, arrow navigation, grouped results, recent queries, a real empty state, and a working no-JS fallback at /search.

3. Contact form hardening: server-side validation, honeypot plus rate limiting, real per-field error states, success state that says what happens next and when, and no silent failures.

4. Insights subscribe: single email field, double opt-in copy, real validation and success states.

5. Dynamic OG images per route via next/og — one template reading page title, type, and practice area. Generate a light-mode variant only (social cards render on unpredictable backgrounds). Verify by fetching three generated images and checking dimensions and that text is not clipped.

6. Breadcrumbs on every nested route with BreadcrumbList JSON-LD. Related-content blocks on service, case study, and article pages.

7. Route-change accessibility: focus moves to the h1 or a skip target on navigation, route change announced politely to screen readers, skip-to-content link as the first focusable element.

8. Analytics and Core Web Vitals reporting wired, with no third-party script blocking first paint.

9. Cookie consent, if and only if analytics sets a non-essential cookie: a real consent banner that blocks the analytics script until consent, remembers the choice, offers a genuine reject option with equal visual weight to accept, and links to /legal/cookies. A pre-ticked or accept-only banner is worse than no banner. If you can configure analytics to be cookieless, do that instead and skip the banner entirely — that is the better answer.

10. Add the registered entity name, company registration number, and a real contact address to the footer base row per spec §8b. If these values are not in the repo, mark TODO(content) — do not invent a registration number.

Then STOP and report: estimator working with JS disabled (screenshot), search keyboard-only (screenshot), three fetched OG images with dimensions, and full gate output — contrast-ci, token-lint, theme-audit, depth-audit, motion-audit, presence-floor, ratio-audit, lint, tsc, tests.
```

**Gate 4 —** estimator and search both function with JS disabled · OG images render without clipped text · every prior gate still passes · no new axe violations in either mode.

## PHASE 5 — verification and performance

```
Read docs/design-spec-v3.md section 13 before starting.

1. Fix mobile performance. The previous build had mobile LCP at 3.1–3.4s. Target: Lighthouse mobile performance ≥90 with LCP <2.5s. Profile first, then fix — report what the actual LCP element is, what is blocking it, and what each change bought. Likely levers: font loading strategy, hero image priority and format, deferring the Capability Graph's animation code, route-level code splitting, and eliminating render-blocking CSS. Do not guess; measure between each change.

2. Lighthouse on / , /services/[a real slug] , /work/[a real slug] , /pricing , /insights/[a real slug] — desktop and mobile, both colour modes. Report all numbers in a table. Desktop ≥98 on all four categories, mobile ≥90 performance.

3. Performance trace with a 4× CPU throttle while the Capability Graph animates and while toggling theme. Report actual frame rates. Must hold 30fps minimum throttled, 60fps unthrottled.

4. Full axe scan, every route, both modes, and also at 200% zoom. Zero serious, zero critical.

5. Manual accessibility pass, documented: complete the whole primary flow — home to service to estimator to submit — using only the keyboard, and report anything that traps focus, is unreachable, or has an unclear focus state. Verify every image has real alt text and that no information is conveyed by colour or motion alone.

6. Screenshot matrix: every major route × light and dark × 1440, 768, 375. Save to docs/screenshots/v3/ with a contact sheet.

7. Answer all 14 questions in spec §13 in writing, in docs/v3-self-audit.md. For question 3 — name the single element that makes this look designed rather than assembled — if you cannot name it, say so plainly rather than reaching.

8. Write docs/v3-deviations.md: every place you departed from the spec, what you did instead, and why. Do not silently freelance; a documented deviation is fine, an undocumented one is not.

9. Deploy to a Vercel PREVIEW only. Do not touch production. Report the preview URL and confirm production and goat-wheat are unchanged.

Then STOP and report everything above. Do not promote to imaginarsclubservices.com under any circumstances — that decision is Soham's alone, made after reviewing the preview.
```

**Gate 5 —** every floor in spec §5 met with measured evidence · Lighthouse table complete for both modes · keyboard pass documented · screenshot matrix complete · self-audit answered honestly · deviations logged · production untouched.
